## Critical Gaps

### 1. Default evaluation does not drive the real scenario command schedule

**Affected requirements:** LOC-ENV-03, LOC-METRICS-01, LOC-EVAL-01, LOC-EVAL-04

`src/locomotion/scenarios.py` creates a first zero command and a later nonzero command. `src/locomotion/evaluation.py` uses `command_schedule[0]` in `_action_from_command_context()` and `_command_fields()` instead of selecting the command active at `sim_time`, and `ArgusGo2Env._info()` does not expose a `current_command`. Because `ArgusGo2Env.step()` treats velocity-mode action as the command, default evaluation can feed `[0.0, 0.0, 0.0]` forever and turn locomotion scenarios into standing-still episodes.

### 2. Evaluation exports `distance_xy_m` from the wrong summary family

**Affected requirements:** LOC-METRICS-02, LOC-METRICS-05, LOC-EVAL-02, LOC-EVAL-04

`src/locomotion/metrics.py` places `distance_xy_m` in the `stability` episode summary. `src/locomotion/evaluation.py` reads `distance_xy_m` from `command_tracking`, defaulting to `0.0`. Real `episodes.csv`, `summary.json`, `comparison.md`, and threshold checks can therefore report zero distance even when the environment recorded distance under stability.

### 3. Evaluation CLI exposes non-default action modes that the runner cannot step

**Affected requirements:** LOC-ENV-04, LOC-EVAL-01, LOC-EVAL-03

`src/main.py` accepts `--action-mode`, and `EvaluationMatrix` carries `action_mode`, but the runner action generator always returns a 3-value command. `ArgusGo2Env` correctly requires 12-value actions for `joint_position` and `residual_baseline`, so `eval-locomotion --action-mode joint_position` or `--action-mode residual_baseline` is accepted at the CLI but cannot complete through the env action contract.
