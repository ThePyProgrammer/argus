## 1. System Classification

**System Type:** Code Automation / Evaluation Repair

**Description:**
This phase repairs robotics evaluation-runner semantics so scheduled locomotion commands, exported distance metrics, analytical baseline thresholds, and regression coverage measure actual movement behavior instead of stationary standing behavior. Good output means the implementation plans and tests force the evaluator to select the current active command, preserve nonzero `distance_xy_m` through artifacts, and prevent baseline checks from passing when locomotion commands are ignored.

**Critical Failure Modes:**
1. Evaluation actions use the first scenario command instead of the command active at the current simulation time.
2. Exported CSV, summary, comparison, or threshold paths drop or zero out `distance_xy_m` despite nonzero locomotion.
3. Regression coverage permits stationary standing behavior to satisfy commanded locomotion scenarios.

## 1b. Domain Context

**Industry Vertical:** Robotics / simulation evaluation tooling for legged locomotion benchmarks

**User Population:** Robotics engineers, locomotion-control researchers, ML evaluation maintainers, and benchmark owners validating quadruped controller behavior in simulated robot environments before comparing controllers or considering hardware transfer.

**Stakes Level:** Medium

**Output Consequence:** If the repaired evaluator is wrong, a controller can be falsely certified as a locomotion baseline even when it ignores scheduled commands, stands still, or loses movement metrics in exported artifacts. That invalidates controller comparisons across scenarios/seeds and can mask defects that would become higher-stakes if the same benchmark results are used to justify hardware experiments.

### What Domain Experts Evaluate Against

Dimension: Active command fidelity
Good (domain expert would accept): Each evaluation step uses the velocity/yaw command active at the current simulation time, and exported command fields match that same active command for the sample or rollout segment being measured.
Bad (domain expert would flag): The evaluator uses the first command in a schedule, a stale reset-time command, or a different command for action generation than for exported metrics.
Stakes: Critical
Source: Practitioner benchmark semantics; legged-locomotion papers evaluate commanded gaits and terrain behavior, so command-conditioned metrics are meaningless if the command source is stale.

Dimension: Movement evidence, not posture survival
Good (domain expert would accept): A commanded forward/lateral/yaw scenario produces nonzero `distance_xy_m` through raw rollout records, CSV export, aggregate summary, comparison table, and threshold checks; a stationary controller fails commanded-locomotion acceptance.
Bad (domain expert would flag): Fall-free standing, base-height stability, or low control effort is counted as success for a scenario that commanded translation or turning.
Stakes: Critical
Source: Locomotion benchmark practice; requirements LOC-METRICS-02/05 and LOC-EVAL-04 explicitly require distance-before-failure/export and regression tests that prevent analytical baseline degradation from passing silently.

Dimension: Scenario and seed comparability
Good (domain expert would accept): Results are grouped by controller, scenario, and seed with mean, standard deviation, and failure counts, so flat-ground, low-friction, slope, rough terrain, and push-disturbance behavior can be compared without mixing conditions.
Bad (domain expert would flag): Aggregates merge incompatible scenarios, omit seed/failure metadata, or hide single-scenario failures behind a global average.
Stakes: High
Source: Benchmark reproducibility practice; requirements LOC-EVAL-01/02 require scenario matrices, fixed seeds, aggregate comparison tables, and failure counts.

Dimension: Robust locomotion under disturbances and terrain variation
Good (domain expert would accept): Evaluation distinguishes command tracking on nominal flat ground from robustness under low friction, slope, rough heightfields, and push disturbances, with failures recorded as locomotion failures rather than missing data.
Bad (domain expert would flag): The same smoke test is treated as evidence for all terrains, disturbances are not reflected in scenario metrics, or failures are filtered out of summaries.
Stakes: High
Source: Legged-locomotion research emphasizes challenging terrain, perturbations, domain randomization, and sim-to-real robustness as core evaluation concerns.

Dimension: Hardware-risk proxy metrics remain visible
Good (domain expert would accept): Smoothness, effort/energy proxy, actuator saturation, joint-limit violations, slip, and fall metrics remain available alongside distance and command tracking so a controller is not selected solely for moving far.
Bad (domain expert would flag): A jerky or saturating controller ranks as successful because distance survived export while control-quality and safety-proxy metrics disappeared from comparison paths.
Stakes: Medium
Source: Robotics RL literature reports that jerky motion patterns can damage real robots; even simulation-only benchmarks should preserve control-quality metrics when results may guide future hardware work.

### Known Failure Modes in This Domain

- **Stale scheduled-command execution:** the rollout starts with a valid schedule but the evaluator keeps using the first command, so later nonzero commands never influence actions or exported command fields.
- **Stationary-success benchmark leakage:** stability/fall metrics let a standing robot pass a locomotion scenario because distance traveled and command-tracking expectations are not part of the baseline gate.
- **Metric evaporation across artifact layers:** `distance_xy_m` or failure counts are computed in the environment but dropped, reset to zero, or renamed inconsistently between JSONL/CSV rows, summaries, comparison tables, and threshold checks.
- **Scenario averaging hides terrain/disturbance failures:** aggregate means look acceptable while low-friction, slope, rough-terrain, or push-disturbance cases fail because results are not stratified by scenario and seed.

### Regulatory / Compliance Context

No direct regulatory requirement is identified for this simulation-only evaluation-runner repair. The relevant constraints are engineering governance rather than formal compliance: deterministic reproducibility, honest benchmark reporting, and preservation of safety-proxy metrics before any result is used to justify real-robot testing. If the benchmark later gates hardware deployment, the safety context changes and should be reviewed under the applicable robotics lab, institutional, and product-safety procedures for physical robot experiments.

### Entry Point Pattern

Minimal copy-paste runner for AI-assisted code review/planning of Phase 6. It reads and tests repository code through tools, but the acceptance contract remains deterministic pytest/evaluation output.

```python
"""Developer-only Claude Agent SDK runner for Phase 6 evaluation repair.

Run from outside production package code. Requires ANTHROPIC auth configured for Claude Code.
"""

import asyncio
from pathlib import Path

from claude_agent_sdk import AssistantMessage, ClaudeAgentOptions, ResultMessage, TextBlock, ToolUseBlock, query

PROJECT_ROOT = Path("/home/prannayag/pragnition/robotics/argus")

SYSTEM_PROMPT = """
You are repairing deterministic robotics evaluation semantics.
Do not add an LLM runtime dependency to the package.
Use tools only to inspect code, make targeted edits, and run pytest/evaluation checks.
Implementation contract:
1. Evaluation runner must select the scenario command active at current simulation time.
2. distance_xy_m must survive CSV, summary, comparison, and threshold export paths.
3. Baseline threshold checks must fail if locomotion commands are ignored.
""".strip()

USER_PROMPT = """
Inspect Phase 6 requirements and implementation code. Produce or apply the smallest code/test changes
that make command scheduling, distance export, and baseline threshold semantics real.
Run deterministic tests that prove the repair.
""".strip()

async def main() -> None:
    options = ClaudeAgentOptions(
        model="claude-sonnet-4-5",
        system_prompt=SYSTEM_PROMPT,
        cwd=str(PROJECT_ROOT),
        max_turns=12,
        max_budget_usd=3.00,
        allowed_tools=["Read", "Grep", "Glob", "Edit", "Write", "Bash"],
        disallowed_tools=["WebFetch"],
        permission_mode="default",
    )

    async for message in query(prompt=USER_PROMPT, options=options):
        if isinstance(message, AssistantMessage):
            for block in message.content:
                if isinstance(block, TextBlock):
                    print(block.text)
                elif isinstance(block, ToolUseBlock):
                    print(f"tool={block.name} input={block.input}")
        elif isinstance(message, ResultMessage):
            print(f"session={message.session_id} cost_usd={message.total_cost_usd:.4f}")

if __name__ == "__main__":
    asyncio.run(main())
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|------------|-----------------|
| `query()` | Stateless async iterator for one-shot agent tasks. | Best fit for a bounded Phase 6 repair prompt where all context can be supplied up front and final proof is pytest output. |
| `ClaudeSDKClient` | Stateful async context manager for multi-turn, bidirectional agent sessions. | Use only if the repair loop needs interactive clarification, interruption, session continuation, or multiple sequential prompts. |
| `ClaudeAgentOptions` | Configuration object for model, working directory, tool access, permissions, budget, output schema, and session behavior. | Central place to pin `cwd`, bound `max_turns`/`max_budget_usd`, select `claude-sonnet-4-5`, and avoid uncontrolled tool use. |
| Tools and permissions | Claude Code toolset exposure plus approval controls such as `allowed_tools`, `disallowed_tools`, `permission_mode`, and `can_use_tool`. | Use for code-aware inspection/edits and shell tests; remember `allowed_tools` is an auto-approval list, not a hard tool allowlist. |
| Hooks | Lifecycle interceptors such as `PreToolUse` via `HookMatcher`. | Use to block dangerous bash patterns, writes to secrets, destructive git operations, or non-deterministic network calls in automation. |
| Structured output | `output_format={"type": "json_schema", "schema": ...}` with `ResultMessage.structured_output`. | Use for machine-checkable repair plans, audit findings, or test plans; validate again with Pydantic in caller code. |

### Common Pitfalls

1. **Adding the SDK to the robotics runtime by accident.** The SDK is appropriate for developer automation, but Phase 6's product contract is deterministic evaluation behavior. Keep `claude-agent-sdk` out of package runtime dependencies unless a later phase explicitly approves an LLM feature.
2. **Misreading `allowed_tools` as a security allowlist.** Official docs note that `allowed_tools` auto-approves listed tools; it does not remove other tools from the Claude Code toolset. Use `disallowed_tools`, `permission_mode`, `can_use_tool`, and/or `PreToolUse` hooks for actual blocking.
3. **Letting the agent prove behavior with prose instead of tests.** Claude can inspect and edit, but acceptance must be pytest/evaluation artifacts proving active command selection, nonzero distance export, and failing baseline checks when locomotion is ignored.
4. **Running with an unbounded turn/cost budget.** Autonomous code agents can loop through inspect/edit/test cycles. Always set `max_turns`, `max_budget_usd`, and an explicit task scope.
5. **Calling `asyncio.run()` inside an already-running event loop.** The SDK is async-first. In notebooks, web servers, or test harnesses with an active loop, `await main()` or schedule a task instead of nesting `asyncio.run()`.
6. **Trusting JSON-shaped text without validation.** Use SDK `output_format` for schema-guided output and then validate `ResultMessage.structured_output` with Pydantic before using it to drive edits or CI decisions.

**Core Pattern:**

The core pattern is **bounded AI-assisted repair loop plus deterministic verification**. Claude may identify and edit code, but the pass/fail gate is pytest/evaluation output.

```python
import asyncio
from pathlib import Path

from claude_agent_sdk import ClaudeAgentOptions, ResultMessage, query
from pydantic import BaseModel, Field, ValidationError

class Phase6RepairReport(BaseModel):
    touched_files: list[str] = Field(default_factory=list)
    tests_run: list[str] = Field(default_factory=list)
    command_schedule_fixed: bool
    distance_export_fixed: bool
    baseline_threshold_fixed: bool
    residual_risks: list[str] = Field(default_factory=list)

REPORT_SCHEMA = Phase6RepairReport.model_json_schema()

async def run_phase6_repair_agent(project_root: Path) -> Phase6RepairReport:
    options = ClaudeAgentOptions(
        model="claude-sonnet-4-5",
        cwd=str(project_root),
        max_turns=12,
        max_budget_usd=3.00,
        allowed_tools=["Read", "Grep", "Glob", "Edit", "Write", "Bash"],
        disallowed_tools=["WebFetch"],
        permission_mode="default",
        output_format={"type": "json_schema", "schema": REPORT_SCHEMA},
        system_prompt=(
            "Repair Phase 6 evaluation semantics. Do not add claude-agent-sdk or any LLM "
            "runtime dependency to package code. Make targeted edits only. Final proof must be "
            "deterministic pytest/evaluation commands."
        ),
    )

    prompt = """
    Fix the evaluation runner so it uses the active scenario command at simulation time,
    exports nonzero distance_xy_m through artifacts, and makes baseline threshold checks fail
    when locomotion commands are ignored. Run the narrowest deterministic tests proving this.
    Return only the requested JSON report.
    """.strip()

    last_result: ResultMessage | None = None
    async for message in query(prompt=prompt, options=options):
        if isinstance(message, ResultMessage):
            last_result = message

    if last_result is None or last_result.structured_output is None:
        raise RuntimeError("Claude Agent SDK did not return structured repair output")

    try:
        return Phase6RepairReport.model_validate(last_result.structured_output)
    except ValidationError as exc:
        raise RuntimeError(f"Invalid repair report schema: {exc}") from exc
```

- Hard-block network and irrelevant tools via `disallowed_tools` where supported.
- For unattended runs, add a `PreToolUse` hook that denies destructive shell patterns, writes to secrets, and adding `claude-agent-sdk` to runtime dependency files.
- Do not use Claude Agent SDK tools as the production evaluator API. They are for developer-assistance only.

**State Management:**

- Source of truth: repository files, Phase 6 planning docs, tests, and evaluation artifacts.
- Agent state: ephemeral per repair run. Use `query()` for bounded one-shot work.
- Persisted evidence: commit-ready diffs, deterministic pytest output, generated CSV/summary/comparison artifacts, and notes in planning docs. These are auditable without Claude.

**Context Window Strategy:**

- Start with the phase spec, relevant evaluator modules, scenario command schedule definitions, export paths, and existing tests. Do not dump the full repository into prompt context.

- Keep invariant bullets short and repeated: active command by time, nonzero distance export, baseline fails when locomotion ignored.
- Treat automatic context compaction as lossy for requirements. Reassert Phase 6 invariants after compaction or session resume.

### 4b.1 Structured Outputs with Pydantic

For Phase 6, structured output is useful for a repair report or audit plan. It must not replace tests. Claude Agent SDK supports JSON Schema output through `ClaudeAgentOptions(output_format={"type": "json_schema", "schema": ...})`; validate the returned `ResultMessage.structured_output` with Pydantic before using it.

```python
from pydantic import BaseModel, Field, ValidationError

class Phase6Finding(BaseModel):
    invariant: str = Field(description="command_schedule | distance_export | baseline_threshold")
    status: str = Field(description="fixed | already_ok | blocked | unknown")
    evidence: str = Field(description="pytest command, artifact path, or code path proving the status")

class Phase6StructuredReport(BaseModel):
    summary: str
    touched_files: list[str]
    findings: list[Phase6Finding]
    tests_run: list[str]
    runtime_dependency_added: bool = Field(
        description="Must be false unless explicitly approved; Claude SDK should stay developer-only."
    )
    residual_risks: list[str] = Field(default_factory=list)
```

Retry policy:
- Try at most **2 validation retries** after the first malformed response.
- Log the validation error, SDK `session_id`, `total_cost_usd`, prompt version, and whether any tools had already modified files.
- On repeated validation failure, surface to the developer and fall back to manual inspection; do not let an invalid report drive edits or CI status.
- Even with valid structured output, require deterministic tests/artifacts for acceptance.

### 4b.2 Async-First Design

Claude Agent SDK is async-first. `query()` returns an async iterator; `ClaudeSDKClient` is an async context manager whose `receive_response()` stream yields messages. Use streaming for supervised code repair and final `ResultMessage` collection for structured validation, cost reporting, and audit trails.

### 4b.3 Prompt Engineering Discipline

Separate instructions by role:
- **System prompt:** non-negotiable behavior and constraints: no runtime LLM dependency, deterministic pytest is the contract, preserve Phase 6 invariants, avoid destructive operations.
- **User prompt:** the concrete repair task: inspect evaluation runner semantics, patch active-command selection, preserve `distance_xy_m`, repair baseline thresholds, run tests.

Token budget discipline:
- Set `max_turns` and `max_budget_usd` in SDK options.
- Ask for concise final reports and artifact paths, not long prose explanations.
- Do not use a weaker model as the sole reviewer for subtle evaluation semantics.

### 4b.4 Context Window Management

This is code automation, not RAG. Manage context by file targeting:
- Read the Phase 6 AI-SPEC/plan first.
- Search for evaluation runner, scenario command schedule, metrics export, comparison, threshold, and baseline code paths.
- Read only the owning modules and adjacent tests.
- Keep a running invariant checklist outside the conversation if doing multiple turns.

### 4b.5 Cost and Latency Budget

Budget for this phase as a developer-assistance task, not production traffic:
- Expected volume: 1-3 supervised repair/audit runs for Phase 6.
- Per-call/run budget: cap at **$2-$3** with `max_budget_usd`; stop earlier once tests prove the invariants.
- Latency target: acceptable in minutes for code repair, but keep pytest scope narrow to avoid simulation sweeps dominating the loop.

## 5. Evaluation Strategy

This phase is an internal robotics evaluation-harness repair, not a production LLM eval suite. The acceptance gate is deterministic code-based regression evidence: pytest fixtures, scenario schedules, generated JSONL/CSV/summary/comparison artifacts, and threshold checks that would fail if the evaluator measured standing posture instead of commanded locomotion.

### Critical Failure Modes Confirmed

1. **Stale scheduled-command execution:** rollout action generation or exported command fields use the first/reset command instead of the command active at current simulation time.
2. **Metric evaporation across artifact layers:** `distance_xy_m` is computed but dropped, renamed inconsistently, rounded to zero, or omitted from CSV, JSONL, summary, comparison, or threshold evaluation.
3. **Stationary-success benchmark leakage:** a controller that ignores locomotion commands can pass because fall-free posture survival is treated as baseline success.
4. **Scenario/seed aggregation blindness:** comparison tables collapse scenario/seed/failure detail and hide terrain, disturbance, or seed-specific failures behind a global average.
5. **Safety-proxy metric disappearance:** movement distance survives, but smoothness, effort, saturation, joint-limit, slip, fall, or base-stability metrics vanish from exported comparison paths.

**Creation Timeline:** Build the fixture set during implementation, before final verification. The first tests should fail against the current broken semantics, then pass after the repair. Do not defer fixture creation until after code changes; otherwise the tests can accidentally encode the patched implementation instead of the intended behavior.

## 6. Guardrails

Phase 6 guardrails are mostly offline/CI because the evaluator is an internal command-line research harness. There is no user-facing online LLM response path to block in real time. The “guardrails” that matter are deterministic acceptance gates that stop misleading benchmark artifacts from being produced or trusted.

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| N/A — no production online user-facing AI path in Phase 6 | The repaired system is an internal deterministic evaluation runner, not a request/response AI service. | No latency-adding online LLM guardrail. Use CLI validation and CI gates instead. |
| CLI artifact sanity check | Evaluation run produces missing/non-finite required metrics, missing `controller_id`/`scenario_id`/`seed`, missing command fields, or absent `distance_xy_m`. | Fail the evaluation command before publishing summary/comparison artifacts; print the missing field/path. |
| Baseline locomotion threshold gate | A commanded-locomotion baseline run reports `distance_xy_m <= minimum_distance_m`, has zero active command after schedule transition, or passes only stability/posture checks. | Mark run failed and fail CI/regression command. Do not certify analytical baseline. |
| Scenario matrix validation | CLI is invoked with an empty scenario list, empty seed list, unknown scenario id, or action/controller mode mismatch that would make results incomparable. | Abort run with a deterministic validation error before simulation starts. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|-----------------------|
| Active command transition correctness | Run all command-schedule fixtures on every PR that touches scenario, controller, evaluator, metrics, or export code. | Block merge until command lookup/export mismatch is fixed. Add a boundary-time fixture for the new failure case. |
| Nonzero-distance artifact preservation | Parse every CI-generated Phase 6 artifact and compare raw rollout `distance_xy_m` to CSV/summary/comparison/threshold values. | Block merge on missing/zero/mismatched distance; add schema assertion for the artifact layer that evaporated the metric. |
| Stationary-controller rejection | Run negative no-op/command-ignoring controller fixture in CI and nightly smoke if simulations are slow. | Block merge if stationary controller passes. Tighten baseline threshold or command fixture if needed. |
| Scenario/seed grouping integrity | For each generated comparison table, assert expected row cardinality, grouping keys, mean/stddev, and failure counts. | Block merge on grouping collapse; require per-scenario/per-seed rows before aggregate rows are trusted. |
| Safety-proxy metric retention | Schema-check smoothness, effort, actuator saturation, joint limits, slip/contact, fall, roll/pitch, and base-height fields in generated exports. | Flag PR for robotics evaluation maintainer review; block if a required metric disappears from comparison artifacts. |
| Threshold calibration drift | Sample analytical baseline flat-ground smoke results over fixed seeds and compare against stored nonzero minimum distance and failure-rate expectations. | Open a calibration issue if the baseline consistently moves outside expected bands; do not silently update thresholds without reviewer sign-off. |

## 7. Production Monitoring

**Tracing Tool:** Local artifact logging and CI trend history. No Arize Phoenix/Langfuse/LangSmith deployment is recommended for Phase 6 because the system is not an online LLM application and no AI eval tracing tool is already configured in the repository. Keep monitoring tied to deterministic robotics artifacts: pytest output, generated JSONL/CSV/summary/comparison files, CI job history, and optional saved run metadata.

**Key Metrics to Track:**

1. **Command fidelity rate:** percentage of schedule-transition samples where exported command fields equal the active command at the recorded simulation time. Target: 100%.
2. **Distance preservation rate:** percentage of runs where `distance_xy_m` is present, finite, nonnegative, and consistent across raw rollout, CSV, summary, comparison, and threshold paths. Target: 100% for commanded-locomotion smoke fixtures.
3. **Flat-ground analytical baseline distance:** mean/stddev of `distance_xy_m` across fixed smoke seeds. Target: above calibrated `minimum_distance_m`; exact value set during implementation with controls-engineer review.
4. **Stationary-controller false-pass count:** number of no-op/command-ignoring controller fixtures that pass commanded-locomotion acceptance. Target: 0.
5. **Scenario/seed coverage:** expected vs. observed result rows for controller × scenario × seed matrix, plus failure counts per scenario. Target: exact expected cardinality; no silently dropped failed rows.
6. **Safety-proxy metric completeness:** percentage of comparison rows with finite smoothness, effort/energy proxy, saturation, joint-limit, slip/contact, fall, roll/pitch, and base-height fields where applicable. Target: 100% field presence for supported metrics.

**Alert Thresholds:**

| Signal | Threshold | Response |
|--------|-----------|----------|
| Command fidelity | Any mismatch between active command and exported/action command in fixture tests. | Fail CI immediately; inspect command schedule lookup and timestamp semantics. |
| Distance export | Any missing `distance_xy_m`, non-finite value, or mismatch beyond deterministic tolerance between artifact layers. | Fail CI; inspect raw-to-CSV/summary/comparison/threshold plumbing. |
| Baseline movement | Analytical baseline flat-ground smoke `distance_xy_m <= minimum_distance_m` or stationary controller passes baseline gate. | Fail CI; do not mark LOC-EVAL-04 complete. |
| Scenario matrix | Observed row count differs from controller × scenario × seed expectation, or failure rows are absent from aggregate comparison. | Fail CI; repair grouping/aggregation before publishing artifacts. |
| Safety-proxy completeness | Required control-quality or stability fields missing from comparison artifacts. | Block benchmark publication; maintainer review required if intentionally deprecated. |
| Runtime practicality | Targeted Phase 6 test gate exceeds the agreed CI budget, e.g. >5 minutes for smoke regression on normal CI hardware. | Split slow simulation checks into nightly jobs, but keep pure schema/fixture checks in PR CI. |

**Smart Sampling Strategy:**

- **Every PR:** run pure unit/schema tests plus the smallest deterministic smoke tests for active command selection, distance export, stationary-controller rejection, and comparison grouping.
- **Scenario-triggered sampling:** when files touching scenario catalogs, command schedules, environment reset/step timing, metrics, exporters, threshold checks, or controller adapters change, run the full Phase 6 fixture set.
- **Nightly or pre-release:** run expanded matrix across flat-ground, low-friction, slope, rough-heightfield, and push-disturbance scenarios with fixed seeds and archive JSONL/CSV/summary/comparison artifacts.
- **Human review sampling:** robotics evaluation maintainer reviews any artifact-schema change; locomotion controls engineer reviews any threshold update, baseline distance drift, or new terrain/disturbance fixture.
- **Failure-mode expansion:** every regression discovered in CI or manual review must add a fixture to the reference set before the fix is accepted. No quiet threshold weakening; baseline threshold changes need explicit reviewer sign-off.
