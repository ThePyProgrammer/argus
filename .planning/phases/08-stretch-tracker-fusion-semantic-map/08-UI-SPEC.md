Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope fence:** Phase 8 touches four frontend surfaces: (1) Three.js scene viewer (new SemanticMapLayer group), (2) pipeline editor NodeInspector (per-robot backend dropdown), (3) MetricsPanel (fused detection row), (4) Zustand stores + WS message types. No new routes, no new full-screen views, no new sidebar sections. Every token below extends -- not replaces -- conventions established by Phase 3 (dark theme dashboard) and continued in Phase 6 and Phase 7.

### SemanticMapLayer OBB Colors (DET-STRETCH-03)

Semantic map wireframe OBBs use per-class colors. The color source is the existing Okabe-Ito colorblind-safe palette (`frontend/src/utils/palette.ts::OKABE_ITO`), mapped by class name hash to a palette index. This reuses the same palette as robot markers and detection boxes.

| Property | Value |
|----------|-------|
| Wireframe color | `OKABE_ITO[hash(class_name) % 8]` -- per-class, colorblind-safe |
| Wireframe opacity (fresh) | 0.7 (matches existing DetectionBoxManager wireframe opacity) |
| Wireframe opacity (at TTL expiry) | 0.0 (fully transparent -- object fades to invisible) |
| Opacity curve | Linear: `opacity = 0.7 * clamp((ttl - age) / ttl, 0, 1)` where `age = sim_now - last_seen` |
| Fill | None -- wireframe only (`wireframe: true` on `MeshBasicMaterial`). No solid fill like DetectionBoxManager uses. Deliberate visual distinction: solid detection boxes = live per-robot; wireframe ghosts = semantic memory. |
| Label sprite | None on semantic map OBBs. Labels clutter at scale when multiple objects persist. Class name available in tooltip/inspector if needed later (deferred). |

**Visual layering order in SceneViewer (locked):**
1. Reconstruction point cloud / voxels / mesh (opaque, existing)
2. Semantic map wireframe OBBs (transparent wireframe, Phase 8 NEW -- renders behind live detections)
3. Per-robot detection OBBs (semi-transparent wireframe + solid fill, existing DetectionBoxManager)
4. Robot markers + trajectory trails (existing)

Render-order enforcement: SemanticMapLayer `<group>` is added to `worldRoot` BEFORE `DetectionBoxManager` group so Three.js painter's algorithm renders semantic ghosts behind live detections. Set `renderOrder: -1` on the semantic map group and `depthWrite: false` on its material.

## Interaction Contracts

### SemanticMap Layer Toggle

1. User sees a toggle control in the ControlPanel sidebar (following the existing `Show Scene` toggle pattern).
2. Toggling ON sets `semanticMapStore.setVisible(true)` -- SemanticMapLayer group becomes `visible = true`.
3. Toggling OFF sets `semanticMapStore.setVisible(false)` -- group becomes `visible = false`. No objects are removed from the store; they resume rendering if toggled back on.
4. Default state: `visible = true` (semantic map is shown when available).

Toggle styling matches existing ControlPanel toggle buttons:
- Active: `background: '#1b5e20'`, `color: '#e0e0e0'`, `border: '1px solid #444'`.
- Inactive: `background: '#37474f'`, `color: '#e0e0e0'`, `border: '1px solid #444'`.
- Size: `padding: '4px 8px'`, `fontSize: 11`, `fontWeight: 600`, `borderRadius: 3`.

### SemanticMap TTL Fade (Three.js)

1. Server sends `semantic_map` WS key per stats tick with `active` (list of objects to add/update) and `expired_ids` (list of fused_track_ids to remove).
2. `semanticMapStore.addOrUpdate(active)` updates the store with latest OBBs + `last_seen` + `ttl` per object.
3. `SemanticMapLayer` subscribes to the store (via `semanticMapStore.subscribe()`, imperative -- same pattern as DetectionBoxManager in SceneViewer).
4. On each render frame (inside the `requestAnimationFrame` loop), SemanticMapLayer iterates active objects and computes per-object opacity: `0.7 * clamp((ttl - (sim_now - last_seen)) / ttl, 0, 1)`. Updates `material.opacity` per instance.
5. On `expired_ids`: removes those OBBs from the instanced mesh and deletes from the store.
6. Net visual effect: objects that are currently observed by any robot render at full 0.7 wireframe opacity. Objects that have left all robots' FOVs gradually fade over their TTL (default 10s) until invisible, then are removed.

### Per-Robot Backend Selection (NodeInspector)

1. User selects a `detector_generic` node in the pipeline editor.
2. NodeInspector renders the existing backend dropdown (Phase 7 D-02 -- all robots).
3. Below the existing dropdown, IF the system has >1 robot (determined from `robotStore.robots.size > 1`), a "Per-Robot Override" section appears with one dropdown per robot.
4. Each per-robot dropdown is pre-populated from `detectorStore.perRobotBackend[robotId]`. Options come from `pipelineStore.availableRegistryNodes` (same source as the main dropdown).
5. Changing a per-robot dropdown fires `POST /api/detectors/select?robot_id={rid}&backend={name}`.
6. On success response, `detectorStore.setPerRobotBackend(rid, name)` updates the store. The RestartOverlay does NOT appear for per-robot swaps (hot-swap, no restart).
7. If the swap fails, an inline error appears: `Backend swap failed for {robot_id}: {detail}` in `#e74c3c` below the dropdown.

### Fused Detection Count in MetricsPanel

1. Server sends `fused_detections` WS key in the stats payload.
2. `metricsStore` stores the array in `fusedDetections`.
3. MetricsPanel renders a new "FUSION" subsection header (styled identically to the existing "DETECTION" subsection header from Phase 6) below the per-robot detection metrics.
4. One metric row: label `fused`, value = `fusedDetections.length` as an integer.
5. When `fusedDetections` is empty or not yet received: displays `0` (not `--`; zero is a valid state meaning no cross-robot fusion matches).

### WS Message Type Extensions

New WS message keys handled by the frontend (not new `type` values -- these are nested keys inside the existing `stats` payload):

| WS Key | Payload Shape | Consumer |
|--------|---------------|----------|
| `fused_detections` | `FusedDetection[]` -- each with `fused_track_id`, `class_name`, `score`, `center`, `half_extents`, `quaternion`, `robot_ids`, `source_track_ids` | `metricsStore.fusedDetections` |

## SemanticMapLayer -- Pixel Spec (locked)

Imperative Three.js manager class. NOT a React component -- follows the `DetectionBoxManager` pattern (class with `update()` / `dispose()` methods, managed by SceneViewer's `useEffect`).

| Property | Value |
|----------|-------|
| Class name | `SemanticMapLayer` |
| File | `frontend/src/components/SemanticMapLayer.ts` |
| Scene parent | `worldRoot` (Z-up rotation applied) |
| Group name | `semantic-map` (string tag for debug inspection) |
| Render order | `-1` on the group (renders behind detection boxes at default `0`) |
| Geometry per object | `THREE.BoxGeometry(hx * 2, hy * 2, hz * 2)` -- same as `DetectionBoxManager` |
| Material | `THREE.MeshBasicMaterial({ wireframe: true, transparent: true, depthWrite: false, color: perClassColor })` |
| Per-class color source | `OKABE_ITO_RGB` via `hash(class_name) % 8` -- stable per class across frames |
| Opacity formula | `0.7 * Math.max(0, Math.min(1, (ttl - (sim_now - last_seen)) / ttl))` |
| Position | `mesh.position.set(center[0], center[1], center[2])` -- world-frame from wire format |
| Orientation | `mesh.quaternion.set(qx, qy, qz, qw)` -- from wire format OBB quaternion |
| Labels | None (wireframe-only for visual clarity at scale) |
| Cleanup on expired | `group.remove(mesh)`, `mesh.geometry.dispose()`, `mesh.material.dispose()` |
| Cleanup on dispose | Iterate all children, dispose geometry + material, remove group from scene |

### Opacity Update Strategy

The opacity of each semantic map OBB must update smoothly per frame, not per WS tick. Two approaches (planner's discretion):

- **Option A (per-frame in animation loop):** SemanticMapLayer exposes an `updateOpacities(simTime: number)` method called from SceneViewer's `requestAnimationFrame` loop. Iterates stored objects, computes `(ttl - (simTime - lastSeen)) / ttl`, sets `material.opacity`. Requires tracking `sim_time` from the most recent stats payload.
- **Option B (per-WS-tick only):** Opacity only updates when a new `semantic_map` WS message arrives (stats cadence, typically 2-5 Hz). Fade appears as discrete steps, not smooth. Simpler but visually choppy.

**Recommendation:** Option A (per-frame) for smooth fade. The `sim_time` is available from the stats payload's `elapsed` field (already consumed by MetricsPanel). Store `currentSimTime` in `semanticMapStore` and update it on each stats tick.
